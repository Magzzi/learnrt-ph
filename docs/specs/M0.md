# M0: Restructure

Status: draft for review. Terms follow [GLOSSARY.md](../../GLOSSARY.md). Milestone outcome from [PRD §12](../PRD.md#12-milestones): *Monorepo; distance and fare logic extracted into `packages/core` with tests; Station graph and Transfers modelled.*

## Why

Every later milestone (offline app, Guided Ride, the live layer) depends on one tested, platform-free source for Lines, Stations, Transfers, fares and distance. Today that logic is spread across Next.js pages, a hardcoded coordinate list and `.xlsx` files parsed in the browser, and nothing is tested.

## User stories

M0 has no rider-facing feature. Its "users" are the developers of M1 and M2, and the riders whose trust depends on correct data.

1. As the M1 developer, I can `import { findNearestStations, getFare, lines, stations } from "@learnrt/core"` and get typed, tested results without React, Next.js, `fetch` or `.xlsx` parsing.
2. As the M2 developer, I can ask the Station graph for a Station's neighbours on its Line and for the Transfers that leave it, so cross-Line route planning has something to search.
3. As the project owner, I can run one command that tests all shared logic, and the existing website still builds and runs from its new location.
4. As a rider (indirectly), I get the same fares the current website gives, because the fare tables are converted from the existing matrices and pinned by tests, not retyped by hand.

## Acceptance criteria

### Monorepo
- A pnpm workspace at the repo root with `apps/web` (the current Next.js site, moved) and `packages/core`. `apps/mobile` and `supabase/` are **not** created in M0.
- `pnpm install` at the root succeeds, and `pnpm --filter web build` produces a production build with the same routes as today (`/`, `/explore`, `/trip`, `/landmark`, `/route`, `/stations`).
- The `.xlsx` files remain in `apps/web/public/` and the web pages keep their current behaviour. Removing them belongs to M4b.
- The root scripts `test` and `typecheck` run across the workspace.

### `packages/core`: distance
- `distanceKm(a, b)` returns the Haversine great-circle distance in kilometres for two `{ lat, lng }` points, using an Earth radius of 6371 km (the same as the current code).
- It returns 0 for identical points and the same value in both directions.

### `packages/core`: network data
- Typed `Line`, `Station` and `Transfer` records, plus `LineStatus` (`operational`, `coming-soon`, `suspended`).
- LRT-1 (25 Stations, including the five Cavite extension Stations), LRT-2 (13) and MRT-3 (13) with `operational` Line Status. Each Station has a stable id (for example `lrt1-doroteo-jose`), a display name, its Line and its coordinates. `stationsOnLine(lineId)` returns a Line's Stations in Line order.
- Line order is taken from the fare matrix headers, and coordinates from `src/app/route/findnearest.ts`. Every Station on these three Lines has coordinates.
- MRT-7 is included as `coming-soon` with the 14 Stations and coordinates already in the repo. Metro Manila Subway, NSCR and PNR are not added in M0; their learn cards are M1.
- The dataset carries `source` and `lastVerified` metadata (PRD §14, data accuracy). Until a rider-trusted source is approved, `lastVerified` is `null`.

### `packages/core`: Nearest Station
- `findNearestStations(point, { limit = 3 })` returns Stations sorted by ascending distance, each with `distanceKm`.
- By default only Stations on `operational` Lines are returned (a change from today, which also returns MRT-7). An option can include other statuses.
- Works with no network access (no geocoding in core).

### `packages/core`: fares
- Fare tables are generated once from the six `.xlsx` files by a checked-in script, into typed data in `packages/core`. The app never reads `.xlsx`.
- `getFare({ line, from, to, ticket: "single-journey" | "stored-value", discounted })` returns a whole-peso amount, or `null` when there is no fare (same Station on a single-journey ticket, or an unknown Station).
- The current website's rules are reproduced exactly and pinned by tests:
  - LRT-1 and LRT-2: table lookup per ticket type. A discounted single-journey fare is `ceil(regular × 0.5)`. A discounted stored-value fare is the regular stored-value fare.
  - MRT-3: a discounted single-journey fare comes from the discounted table; every other case comes from the regular table, which is used for stored-value too.
  - Lookup is directional (origin column, destination row), as today, so the known asymmetries in the source tables are preserved, not "fixed".
- A test compares every cell of the generated tables against the `.xlsx` files, so the conversion is provably lossless.

### `packages/core`: Station graph and Transfers
- Three Transfers: LRT-1 Doroteo Jose ↔ LRT-2 Recto, LRT-1 EDSA ↔ MRT-3 Taft Ave, LRT-2 Cubao ↔ MRT-3 Cubao. These are named in PRD §9 and in the existing landmark data. Walking time, distance and directions are left empty (see data-todo).
- The graph exposes, for any Station, its adjacent Stations on the same Line and the Transfers that start from it. Transfers work in both directions.
- Tests prove that LRT-1, LRT-2 and MRT-3 form one connected network through the Transfers, and that `coming-soon` Lines are not connected to it.

## Edge cases
- Same origin and destination: a single-journey fare returns `null`. A stored-value fare returns the table's diagonal value (16 on LRT-1, 13 on LRT-2), because the source tables contain it; flagged in data-todo.
- An unknown Station id, or a Station on a different Line than `line`: returns `null` rather than throwing.
- Two different Stations named "Santolan" (LRT-2, MRT-3) and two named "Cubao": ids must differ, and lookups go by id, never by display name.
- Points far outside Metro Manila still return the nearest Stations. No 100 km cut-off exists in the current code (CLAUDE.md says otherwise; that line gets corrected).
- A Cavite extension Station whose operating status is unconfirmed is still modelled as a normal Station. Station-level status is out of scope (see data-todo).

## Out of scope
- `apps/mobile`, Expo, any UI (M1).
- Route planning or pathfinding across Transfers, fares for cross-Line trips (M2).
- Supabase, SQL schema, the SQLite snapshot (M3).
- Deleting web pages, `.xlsx` files or unused dependencies (M4b).
- Headway Estimate (it needs published headways, which are unknown), operating hours, open/closed logic.
- Geocoding (Nominatim stays in the web app; it is not offline).
- Correcting any data value. Suspected errors are recorded, not changed.

3. `pnpm -r typecheck` passes.
4. `pnpm --filter web build` succeeds and lists the same six routes.
5. `pnpm --filter web lint` result is reported. It may already fail before M0, because `next lint` was removed in Next 16; if so, that is recorded, not hidden.
6. The fare round-trip test covers every non-empty cell in all six matrices.
